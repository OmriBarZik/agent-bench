You have clangd, a C and C++ language server, in this session, through the tool named `LSP`. It covers `.c`, `.cc`, `.cpp`, `.h`, `.hh`, `.m`, and `.mm` files. It was added to help you with this task. Use it wherever it fits, starting with your first look inside a C++ file. It is not an MCP server and not a Bash command. It is already allowed. If `LSP` is not in your tool list yet, load it with tool search, read its schema, and then call it. Loading it is not using it.

**When it beats `grep` in this checkout.** Chromium's browser and renderer code is C++, and a full Chromium build takes a long time. When a Chromium task reaches C++, you have to work out what a class offers and what type a value has, and write code that compiles without spending a build on every mistake.

- `documentSymbol` lists every class, method and field of a file with its line. That answers "what does this class have?" without reading the file or guessing names to `grep` for.
- `hover` gives the exact type of a variable, parameter or return value, and `goToDefinition` follows a name through its includes to where it is defined. Chromium's types (`scoped_refptr`, `raw_ptr`, callbacks) are hard to get right from text alone.
- `findReferences` and `incomingCalls` return the real uses of a symbol in the files clangd has opened, without the comments, strings and longer names `grep` returns.
- After every Edit or Write on a covered file, diagnostics come back by themselves. They are the compile check for that file, seconds after the edit, where a build shows the same error much later.

**When it does not.** It cannot find a file by name or by text: locate files with `ls` and `grep` through Bash. It has no index of the tree and only knows the files it has opened, so "who uses this anywhere in Chromium?" is a `grep` question. It knows nothing about TypeScript, JavaScript, `BUILD.gn`, `.gni`, `.idl`, `.mojom`, `.json5` or `.grd` files; silence on those is not a compile result. If the task touches no C or C++ file, clangd has nothing to do in it: say so in one sentence and work with `grep`. These diagnostics are not a compile result, so do not rewrite a file because of them: the file has no compile command, the server failed to start, or the message names a generated header that does not exist yet. The header generated from an `.idl` or `.mojom` file you added exists only after a build, so "file not found" for it, and the errors that follow from it, are expected.

**Start with it.** Before your first search, decide what you will use `LSP` for in this task and say so in one sentence. Make your first code search inside a C or C++ file with `LSP`: when `ls` or `grep` has given you the file, call `documentSymbol` on it instead of reading it or grepping it for names. You must use `LSP` for every question about a definition, the references, the callers or the type of a C or C++ symbol. The baseline rule that sends a search to `grep` through Bash is the fallback for the searches `LSP` cannot do. It is not where a search starts. When `LSP` cannot answer, or returns an error or nothing, use `grep` for that one question, and come back to `LSP` for the next one that fits.

**Three questions a Chromium task asks, and how `LSP` answers them.**

- What can a web UI element do, and who calls it? Web UI is TypeScript, which clangd does not cover: use `grep` through Bash.
- Which build target compiles a file? `BUILD.gn` files are not covered either: use `grep` through Bash.
- What does the preference service offer, and what does it hold? `{"operation": "documentSymbol", "filePath": "components/prefs/pref_service.h", "line": 1, "character": 1}` lists the class. In `components/prefs/pref_service.cc`, `hover` and `goToDefinition` on `user_pref_store_` show its type and where it is declared. Which build target compiles a file is a text question: use `grep` for it.

**How to call it.** Every call takes `operation`, `filePath`, `line` and `character`; `line` and `character` are 1-based and must point at the symbol's name. Get them from a `documentSymbol` result or from `grep -n`. The operations are `documentSymbol`, `goToDefinition`, `findReferences`, `hover`, `incomingCalls`, `outgoingCalls`, `prepareCallHierarchy`, `goToImplementation`, and `workspaceSymbol` (which also takes `query`). The first call on a file can take a while, because clangd parses it then. Do not wait for it to index the tree: it will not.

After every Edit or Write on a covered file, read the diagnostics that come back. Fix an error your edit introduced before you move on, and do not finish while a file you changed still has a diagnostic your edit caused.

**Rules.** The shell stays at the checkout root. Do not use `cd`. Edit and Write remain the way to change a file. The baseline shell rules still apply.
