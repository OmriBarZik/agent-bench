You have two language servers in this session, through the tool named `LSP`. clangd covers `.c`, `.cc`, `.cpp`, `.h`, `.hh`, `.m`, and `.mm` files. The TypeScript language server covers `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, and `.cjs` files. They were added to help you with this task. Use them wherever they fit, starting with your first look inside a source file. They are not MCP servers and not Bash commands. `LSP` is already allowed. If it is not in your tool list yet, load it with tool search, read its schema, and then call it. Loading it is not using it.

**When it beats `grep` in this checkout.** Chromium's web UI is TypeScript and JavaScript, often in long files; its browser and renderer code is C++, and a full Chromium build takes a long time. A Chromium task has you working out what a class offers, who calls a method, and what type a value has, so that your change compiles without spending a build on every mistake.

- `documentSymbol` lists every class, method and field of a file with its line. That answers "what does this class have?" without reading the file or guessing names to `grep` for.
- `findReferences` and `incomingCalls` return the real uses of one method or field. `grep` for the same name also returns comments, strings and longer names.
- `hover` gives the exact type of a field, variable, parameter or return value, and `goToDefinition` follows a name through its imports or includes to where it is defined. Both tell you what you may write before a build tells you what you got wrong.
- After every Edit or Write on a covered file, diagnostics come back by themselves. They show an error seconds after the edit, where a build shows it much later.

**When it does not.** It cannot find a file by name or by text: locate files with `ls` and `grep` through Bash. clangd has no index of the tree and only knows the files it has opened, so "who uses this anywhere in Chromium?" in C++ is a `grep` question. Neither server knows `BUILD.gn`, `.gni`, `.idl`, `.mojom`, `.json5` or `.grd` files; silence on those is not a compile result. These diagnostics are not a compile result, so do not rewrite a file because of them: a C++ file has no compile command, a server failed to start, the message names a generated header that does not exist yet, a TypeScript import such as `chrome://resources/...` cannot be found, or a `possibly 'null'` or `not assignable` error follows from that missing import on a line you did not change (web UI sources under `components/` resolve those imports through a `tsconfig.json` at the checkout root, so this only happens in other TypeScript directories, which have no `tsconfig.json` next to their sources), or the diagnostic is on a symbol you did not touch. The header generated from an `.idl` or `.mojom` file you added exists only after a build, so "file not found" for it, and the errors that follow from it, are expected.

**Start with it.** Before your first search, decide what you will use `LSP` for in this task and say so in one sentence. Make your first code search inside a covered source file with `LSP`: when `ls` or `grep` has given you the file, call `documentSymbol` on it instead of reading it or grepping it for names. You must use `LSP` for every question about a definition, the references, the callers or the type of a symbol in a covered file. The baseline rule that sends a search to `grep` through Bash is the fallback for the searches `LSP` cannot do. It is not where a search starts. When `LSP` cannot answer, or returns an error or nothing, use `grep` for that one question, and come back to `LSP` for the next one that fits.

**Three questions a Chromium task asks, and how `LSP` answers them.**

- What can a web UI dialog element do, and who cancels it? `{"operation": "documentSymbol", "filePath": "ui/webui/resources/cr_elements/cr_dialog/cr_dialog.ts", "line": 1, "character": 1}` lists the class. Then `findReferences` with the line and character of `cancel` from that list returns its callers.
- What is a name a file imports, and where does it come from? In the same file, call `hover` and `goToDefinition` on `CrInputElement`.
- What does the preference service offer, and what does it hold? `{"operation": "documentSymbol", "filePath": "components/prefs/pref_service.h", "line": 1, "character": 1}` lists the class. In `components/prefs/pref_service.cc`, `hover` and `goToDefinition` on `user_pref_store_` show its type and where it is declared. Which build target compiles a file is a text question: use `grep` for it.

**How to call it.** Every call takes `operation`, `filePath`, `line` and `character`; `line` and `character` are 1-based and must point at the symbol's name. Get them from a `documentSymbol` result or from `grep -n`. The operations are `documentSymbol`, `goToDefinition`, `findReferences`, `hover`, `incomingCalls`, `outgoingCalls`, `prepareCallHierarchy`, `goToImplementation`, and `workspaceSymbol` (which also takes `query`). The first call on a C++ file can take a while, because clangd parses it then. Do not wait for it to index the tree: it will not.

After every Edit or Write on a covered file, read the diagnostics that come back. Fix an error your edit introduced before you move on, and do not finish while a file you changed still has a diagnostic your edit caused.

**Rules.** The shell stays at the checkout root. Do not use `cd`. Edit and Write remain the way to change a file. The baseline shell rules still apply.
